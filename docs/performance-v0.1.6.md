# v0.1.6 检索工程基准

测量日期：2026-10-10。对照基线：Git `9a12067`（v0.1.5）；本次只读目录枚举与 SQLite 增量保存优化，不涉及 MFT／USN 或 LLM。

## 方法与环境

Windows NT 10.0.26200，.NET 10.0.9，16 个逻辑处理器，工作区为 NTFS；运行时报告可用内存上限约 15.4 GiB（不等同独立硬件测量）。工作区本地磁盘类型／SSD 型号和物理内存没有独立测量，不将它当作正式参考机。文件夹具在 artifacts 内自动生成；未读取个人目录。

目录夹具：1 万个文本文件、1,000 个子目录、额外 100 个 package.json，识别 100 个项目，总计 10,200 个资产。基线／新版交替运行三轮，结果数量均一致。文件刚创建，操作系统缓存较热，不等同冷启动全盘扫描。

存储夹具：10 万条模拟资产，先首次保存，再无变化保存、修改设置、修改一个标签。每种操作仅测一次；旧版／新版使用独立 SQLite 文件，并校验数量和标签。旧版扫描与存储代码冻结在基准工具中，仅作对照，不供产品运行。

## 实测

| 操作 | v0.1.5 | v0.1.6 | 说明 |
| --- | --- | --- | --- |
| 目录扫描（三轮中位数） | 927 ms | 267 ms | 同一夹具中约 3.47 倍；不含持久化和 WPF |
| 10 万条首次保存 | 2,019 ms | 1,947 ms | 新版写入 100,001 行 |
| 无变化保存 | 2,479 ms | 538 ms | 新版写入 0 行 |
| 修改设置保存 | 1,521 ms | 424 ms | 新版写入 1 行 |
| 修改一个标签保存 | 1,676 ms | 426 ms | 新版写入 1 行 |

整个基准进程（包含两套引擎、夹具和恢复校验）的峰值工作集约 268 MiB，不能作为产品内存验收结果。原始机器可读结果见 [performance-v0.1.6.json](performance-v0.1.6.json)。开发期间多次测量出现明显波动，本表是最终实现的一次对照；尤其首次保存不宣称稳定加速。

## 如何复现

在仓库根目录运行：

```powershell
dotnet run --project tools/AssetDesk.Benchmarks/AssetDesk.Benchmarks.csproj -c Release -- 10000 100000
```

参数分别为生成的文本文件数和模拟资产记录数。结果及隔离文件夹具写到 artifacts/benchmarks 下的新目录；不复用个人数据库，不自动删除已有目录。较大参数会增加生成耗时、内存和磁盘占用。

## 收益与未解决问题

- 项目标记直接从枚举返回的名字识别，减少原先每目录多次 File.Exists／Directory.Exists；保护路径不再为每个文件重新构造。
- 指纹差异与事务 UPSERT／删除避免全库重写，维持资产身份、标签和未变化行的顺序；外部连接写入时使指纹快照失效。
- 仍会序列化、比较全部内存对象，所以修改单项的 CPU 成本仍随资产总数增加；初次大量写入不会获得同样收益。
- 搜索仍为内存线性筛选，启动仍加载全索引；本次未验证搜索 P95、冷启动、百万资产或真实全盘耗时。
- MFT／USN、变化监听、结构化索引分页、有界流式写库与磁盘类型自适应仍待开发。预扫描时间估算仍为未校准的 2–6 倍启发式，并未因此升级为预测模型。

本报告用于定位和验证局部瓶颈，不宣称普遍速度提升倍数或已达到完整性能验收。
