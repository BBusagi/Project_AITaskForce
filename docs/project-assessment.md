# 项目评估

v0.1.4 当前调整：磁盘下拉框展开时自动刷新磁盘清单；原“刷新磁盘”按钮替换为“预扫描”。预扫描只读遍历同一排除规则下的文件／项目，统计当前可枚举数量，不创建资产、不写库；记录在本次会话内显示，重启不保留。支持暂停、取消、错误／排除计数；全电脑的注册应用／PATH 发现不计入估算。时间暂为枚举耗时 2–6 倍的未校准启发式区间，不保证覆盖 UI／合并／写库开销；取消或错误导致部分范围时不估算总耗时。正式扫描不设固定数量上限，仍受内存、存储、权限和排除规则限制，尚未证明百万资产性能。新扫描策略使旧达限缓存不再匹配，旧记录保留为历史。检索框仅在指定目录模式显示；全电脑／按磁盘模式隐藏并清空筛选。AI 保持冻结。

版本：0.1；日期：2026-10-10；状态：设计草案。

## 1. 评估结论

值得开发。建议定位为“个人电脑资产管理工作台”：整合分散在文件资源管理器、应用设置、磁盘目录、开发工具和 Git 中的信息，让用户通过一个 GUI 理解并管理电脑。

首版不承诺全自动整理、所有应用完全识别、广告软件准确检测或一键安全清理。优先证明：无需改变原有目录结构，用户也能找到文件、理解应用占用、看清开发环境和项目。

Windows 为当前平台假设；单机、单用户、本地优先。先服务开发者个人，再验证普通用户体验。普通用户和开发者共享资产索引，开发者面板可选开启。

## 2. 用户问题与产品价值

| 用户问题 | 对应产品能力 | 能力边界 |
| --- | --- | --- |
| 文件散落在不同磁盘，下载和截图难找 | 跨目录索引、搜索、类型与标签视图 | 文件不需要移动 |
| 安装的软件多，来源和用途不清楚 | 应用清单、来源证据、用途分类、系统设置入口 | 不保证完整发现便携软件 |
| 占用空间越来越大 | 分类占用、目录占用、大文件、候选重复项 | 占用大不等于可删除 |
| 开发环境版本和位置混乱 | 运行时、SDK、版本管理器与 PATH 来源面板 | 已发现安装不等于实际可用 |
| 本地项目很多，不清楚哪些是 Git 项目 | 项目发现、仓库状态、技术栈、路径导航 | 不自动运行项目代码 |
| 历史安装和广告植入导致疑虑 | 新发现应用、自启动项和未知来源提示（后续） | 来源未知不等于恶意或广告软件 |

产品核心价值是把“文件—应用—环境—项目”的关系放到一起。能否形成真实差异化和付费意愿，仍需用户访谈与可用性验证；本次不是完整市场调研。

## 3. 可行性与主要难点

| 模块 | 可行性 | 难度 | 主要原因 |
| --- | --- | --- | --- |
| 文件元数据扫描、按类型筛选 | 高 | 中 | 权限、超大目录、符号链接、云占位文件 |
| 已安装应用清单 | 高，但覆盖有限 | 中 | 安装渠道与注册信息不统一 |
| 照片和截图区分 | 规则初筛可行 | 中 | 同为图像文件，命名和路径只能提供线索 |
| 开发环境与本地项目发现 | 高，需限定生态 | 中至高 | 多版本、虚拟环境、WSL、容器与版本管理器 |
| 全盘增量索引 | 高 | 高 | 事件丢失、离线磁盘、扫描期间变化 |
| 应用与目录归属关系 | 部分可行 | 高 | 共享组件与缺失的安装元数据 |
| 自动判断广告软件或垃圾文件 | 不宜作为通用保证 | 很高 | 判断依据不充分，误判后果大 |
| 自动搬迁应用、运行库和项目 | 不建议首版 | 很高 | 路径、配置、依赖和权限可能失效 |

微软明确指出，没有保证发现系统上每个应用的方法；常规卸载注册表信息和当前用户包清单可以作为主要发现渠道。[软件安装查询说明](https://learn.microsoft.com/en-us/powershell/scripting/samples/working-with-software-installations)、[PackageManager 文档](https://learn.microsoft.com/en-us/uwp/api/windows.management.deployment.packagemanager.findpackagesforuser)。

因此必须展示扫描覆盖范围、失败和未知结果，不能将“未发现”当成“不存在”。

## 4. 分类模型的修正

“系统／系统外”适合作为概览，但不足以决定管理权限。建议同时使用三个维度：

1. 归属：系统组件、应用程序、应用数据、开发资产、个人文件、未知。
2. 内容类型：图像、视频、音频、文档、压缩包、源代码、安装包等。
3. 保护状态：系统保护、依赖保护、用户保护、可整理候选、待确认。

例如 Python 虚拟环境属于开发资产，也属于项目依赖；截图属于图像，也可以带“工作／项目 A”标签。分类可以多重关联，但统计必须去重。

“可整理候选”只表示可供人工评估，绝不自动赋予删除权限。未知对象必须保留为未知。

## 5. 是否需要 LLM

更新结论：扫描器和基础索引不需要 LLM，但用户确认 AI 辅助与管理是产品核心，因此首版接入 LLM 的粗分类、标签建议和解释。用户审核后才采用，文件内容辨别和真实删除仍由用户决策。AI 暂不可用时，基础管理可以独立工作。

| 功能 | 首选实现 | LLM 是否必要 |
| --- | --- | --- |
| 发现文件、应用、版本与路径 | Windows API、元数据、规则 | 不需要 |
| 识别 Git 和技术栈 | Git 元数据、项目清单文件 | 不需要 |
| 大文件和候选重复项 | 大小筛选、按需完整哈希 | 不需要 |
| 基础用途分类 | 本地规则、用户标签 | 不需要 |
| 解释开发环境冲突 | 规则判断；LLM 可解释证据 | 可选 |
| 自然语言查找 | 本地查询；LLM 可转换查询条件 | 可选 |
| 文件内容语义分类 | 内容解析、OCR、嵌入或 LLM | 按需求评估 |
| 广告软件／恶意软件判断 | 专门的安全证据与检测系统 | LLM 不能作为权威判定器 |
| 删除、移动、卸载审批 | 明确规则、对象复核与用户确认 | 不能交给 LLM 独立决定 |

图像内容识别可能需要视觉模型；普通文本 LLM 不能仅凭扩展名判断图片内容。嵌入模型、OCR 和 LLM 是不同能力，应按需求分别选择。

若引入云模型，文件名、路径、项目名和仓库地址也属于可能敏感的数据。默认不上传内容、密钥、环境变量、Git 凭据或完整目录树。用户需看到本次拟发送的数据并选择范围。

AI 输出仅生成结构化建议或查询条件，经本地校验后展示；文件名和文档中的指令不具备执行权限。离线或模型失败时，扫描、搜索和 GUI 仍完整工作。

## 6. 技术方向

在“Windows 优先、单人开发、系统集成较重”的假设下，建议 C# + WPF + SQLite，本地应用内部运行扫描服务，不先引入云后端或常驻高权限服务。

WPF 提供数据绑定、布局等桌面 UI 能力，且只运行在 Windows；该平台限制需要接受。[WPF 官方说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)。

建议模块：桌面 UI → 查询与资产服务 → SQLite；后台扫描调度器 → 文件、应用、开发环境、项目发现器 → 分类规则与关系构建 → 索引。

如果开发者主要熟悉 React，Electron + TypeScript UI + C# 扫描进程也是可选方案，但会增加进程通信、打包和权限边界的工作量。跨平台成为明确目标后，再评估跨平台 UI 与各 OS 的独立扫描适配器。

具体 .NET、SQLite 包版本在实施时验证并锁定。本阶段不以“最新版本”作为架构理由。

## 7. 范围与路线

当前交付基线为 v0.1.3：七项侧栏、独立文件导航与总览快捷入口、人工分类、应用视图、可复制记录、扫描快照与 SQLite；AI 页面保留但冻结。底层 AI／缓存能力存在，不表示界面可使用。

后续以 [开发路径](development-roadmap.md) 为准：

- 检索先建立性能基准，再优化合并、增量写库、索引查询与 UI，随后实现增量更新，最后评估 NTFS MFT／USN。
- AI 先重设计功能与交互，评审后恢复有限范围提案和人工审核，随后依赖增量索引实现变化范围分析及预算控制。
- 固定扫描数量限制已解除，规模性能仍须验证，历史部分记录仍为部分覆盖。

WSL／容器、正文／OCR、重复项哈希、真实文件整理与恶意软件识别保持后置；不纳入自动系统清理、驱动／内核开发或通用杀毒。

## 8. 估算与立项门槛

以下为一名熟悉 C#／Windows 桌面开发者全职工作的规划估计，不是承诺；假设不做真实清理、不做内容 AI、不做 WSL 深度集成。

| 阶段 | 交付物 | 估计 |
| --- | --- | --- |
| 技术验证 | 扫描、应用枚举、项目发现、10 万文件试验 | 1–2 周 |
| 核心索引与发现器 | 数据模型、规则、暂停恢复、检测证据 | 2–3 周 |
| GUI 与查询 | 六个核心页面、标签、搜索、详情 | 2–3 周 |
| 验证与发布准备 | 异常目录、长路径、权限、打包、性能检查 | 2–3 周 |

合计约 7–11 周是完整资产可见性 MVP 的原始规划估计，不是本次原型开发耗时或交付承诺；学习成本、跨平台或安全清理会显著增加工期。首版已增加本机与云端 LLM 适配，需单独衡量模型延迟、资源和分类质量，并计入 API 用量预算。主要成本仍是工程与测试。

继续投入的门槛：技术验证确认扫描不阻塞 UI；已知测试资产可被准确发现；用户能在同一界面回答“有什么、在哪里、归谁、是否已扫描”；邀请 3–5 位目标用户验证查找和理解资产的任务。这是探索性验证，不足以证明市场规模。

## 9. 关键工程依据

- 应用元数据来源：[卸载注册表字段](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key)。安装大小可能缺失或只是估计，应与本工具测量值分开展示。
- 目录连接和其他特殊对象：[Reparse points](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/reparse-points)。扫描不盲目递归跟随。
- 持续变更发现：[NTFS change journals](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals)。作为后续优化，并非跨文件系统通用方案。
- 目录监听会丢失事件：[FileSystemWatcher 缓冲溢出](https://learn.microsoft.com/en-us/dotnet/api/system.io.internalbufferoverflowexception)。需用重扫补偿，不能当唯一事实来源。
- 仓库路径与工作树确认：[git rev-parse](https://git-scm.com/docs/git-rev-parse)。发现目录标记后仍需验证仓库类型。
